# aobs — Amnesic Offline Bitcoin Signer

A Bitcoin signing appliance shipped as a bootable Debian LiveCD (`bitcoin-signer-amd64.iso`, amd64 only). The user boots it, loads or creates a wallet, signs a PSBT, and shuts down. The wallet lives in RAM and nothing survives the session.

## Status: the spec is closed; the image matches it again; the Rust does not yet

The v1 implementation spec is written and merged — `docs/specs/` (seven files, the last being the code registry added by [#56](https://github.com/allisson/aobs/issues/56)), `docs/adr/` (seventeen ADRs, one of them superseded) and `CONTEXT.md`, assembled from 27 closed decision tickets plus the display-path map ([#42](https://github.com/allisson/aobs/issues/42)).

**A walking skeleton is on `main`** ([#39](https://github.com/allisson/aobs/issues/39)): `aobs/` and `aobs-core/`, `ci/`, and `image/` with the live-build config, hooks and the `aobs.service` unit. It is what falsified ADR-0009 by building an ISO and booting it.

**`image/`, `ci/` and the crate's backend feature were reconciled against ADR-0016 and the panel map by [#57](https://github.com/allisson/aobs/issues/57)** — no seatd, no `libseat1`, `backend-linuxkms-noseat`, `Type=notify`, `console-detach`/`console-attach`, the GPU modules deleted, the keymap pinned, and `TTYVTDisallocate=yes` gone for the reason [#52](https://github.com/allisson/aobs/issues/52) proved.

**That reconciliation has now been built and booted** ([#65](https://github.com/allisson/aobs/issues/65)): the ISO builds from `main` with no manual steps, `ci/check-image.sh` passes, and it draws and prints `AOBS_READY` on both QEMU machine types — `ramfb` with no GPU, which is the fbdev tier ADR-0016 rests on, and virtio-gpu. #52's `fbcon` probe is a standing row (`ci/fbcon-probe.sh`): two NMIs after readiness leave the panel byte-identical on a boot where the appliance started exactly once. Building it found one defect and fixed it — the unit was `Type=notify` and nothing in the crate ever sent `READY=1`, so `aobs/src/notify.rs` now does.

**The two gates that judge code are wired before the code exists** ([#66](https://github.com/allisson/aobs/issues/66)): `ci/check-coverage.sh` holds `aobs-core` to 95% **region** coverage and each of the nine components named in `ci/coverage-components.tsv` to 98%, and `ci/check-fuzz.sh` builds and runs the fuzz harness on a placeholder target. Both are separate CI jobs from the test run, because §1 says coverage is necessary and not sufficient. A component whose module does not exist yet is a name with no regions rather than a hole in the list — which is the point of wiring them now: a gate added afterwards is a gate negotiated with the code it is supposed to judge. `ci/check-source-test.sh` is the test on the test, planting each forbidden coverage opt-out attribute in the tree and asserting `ci/check-source.sh` still refuses it.

**The appliance learns its mode at startup and acts on it** ([#68](https://github.com/allisson/aobs/issues/68)): `aobs/src/display.rs` computes `scale = max(1, min(w/1280, h/800))` from the mode the display handed back and dispatches `ScaleFactorChanged`, refuses below the 800×600 floor with `AOBS-E06` before any UI is shown, and names the tier on the readiness line by **observing** which device Slint actually opened. `fail.rs` now carries `E01`–`E06` as `06-codes.md` §5 defines them, with `E02` narrowed and its legacy-BIOS copy gone. Four CI rows assert it, geometry set with QEMU's `xres`/`yres` rather than `SLINT_DRM_MODE` — `05-testing-and-release.md` §6.2 records why.

**The appliance boots to something a person can use** ([#69](https://github.com/allisson/aobs/issues/69)): `aobs/ui/app.slint` is the shell frame — chrome that no screen can remove, one `FocusScope` in the frame owning every key, and the *restart / shut down* row appended to every screen's ring so §7's *always* is structural rather than remembered. §1's flat three-entry start menu is there, with the camera entry visibly unavailable and its reason stated when `/dev/video*` is absent. §13's confirm ends the session: `aobs/src/router.rs` marshals intents to screens and nothing else — no arm inspects a value — and *shut down* is `exit 42` while *restart* is `exit 0`, with a test tying both to the unit's own `SuccessExitStatus=`. `aobs/src/power.rs` reads `KEY_POWER` off the `Power Button` evdev node found by name in sysfs, no crate and no ioctl, and routes it through the same intent the footer row fires. Building it found the defect that made the whole contract inert: `/usr/lib/aobs/launch` fell through to `AOBS-E00` on **every** status, so `exit 42` never reached systemd and a crash parked instead of restarting. `ci/power-button-probe.sh` is §6.2's power-button row, which had been waiting for a shutdown to assert on.

**The four accounts exist, and the identity facts with them** ([#71](https://github.com/allisson/aobs/issues/71)): `aobs-core/src/derive.rs` is `Wallet::load` — BIP44/49/84/86 at account 0 on the loaded network, derived together, with no argument anywhere that selects a script type or an account index. `Network` is two states because nothing in a key, an address or a descriptor tells testnet from signet. The vectors are the BIPs' own tables for the `abandon … about` mnemonic, and BIP-86's published root pins seed and master derivation too; **BIP-44 publishes none**, so that family is cross-checked against the same path derived from that root through the dependency — §2's row now says so. The master xprv joins the wrapped secret list as its 78-byte serialisation, because `Xpriv` is the dependency's type and is not `ZeroizeOnDrop`; `Wallet::with_master` is the only way back to one and erases the copy it decodes. `format.rs` carries the address half of the ninth component — 4-character groups as data, since the separation is a sub-cell gap and never a space.

**Every number on the review panel now has a rule** ([#100](https://github.com/allisson/aobs/issues/100)): `04-screens.md` §11.2.1 is the decision and `format.rs` is it as code — BTC with eight decimals never trimmed, because the fixed point makes a magnitude error a misaligned column; satoshi digits grouped in **threes** as data, the same sub-cell gap as an address and deliberately not the same group size, since four is for characters compared one at a time and three is for digits read as a magnitude; the fee alone carrying that second form, because it is the number eight decimals serve worst. Two roundings would have made the formatter an evaluator and both are bounded instead: a real fee under 0.05 sat/vB is `< 0.1` and a real ratio under 0.0005% is `< 0.001`, never `0.0` or `0.000`. The percentage's denominator is the amount paying — §9's own warning denominator — so a consolidation returns **nothing** rather than a zero, an infinity or a dash. The one thing no spec text had answered at all: the rate divides by the **predicted vsize of the signed** transaction, summed in weight units and charged the smaller 71-byte ECDSA signature element, so **the displayed rate is never lower than what will be paid**; the prediction against a real signed transaction is a new owed measurement.

**A wallet can be created, and the first owed measurement is discharged** ([#72](https://github.com/allisson/aobs/issues/72)): `aobs/src/create.rs` is 04-screens.md §2 and §3 — one screen gathering dice while `getrandom(2)` blocks behind it, then the phrase in **two column-major columns of 12**, which is the part a row-flow grid would invert while passing every arithmetic check, so the split is Rust with a test rather than a slice taken in Slint. The wait is indeterminate seconds and it only *unlocks* Continue; the roll count is the whole of what the screen says about the rolls, because a running hash would hand back the property the XOR mix exists to have. Two threads and no timeout: the camera frame cannot hold up the syscall that unlocks Continue, and a frame that never arrives is the camera-less case core already handles. The wallet's 32 bytes come from `aobs/src/entropy.rs`'s one raw syscall — the site the provenance gate traces — and the dice buffer, the luma plane, `csprng_32` and the supplement are all gone by the time `entropy` exists, because `mix` takes every one of them by value. **The camera arrives here rather than with #78**: `v4l` at default features, `GREY` or `YUYV` and never `MJPG`, one frame, no preview — and it costs the build environment `libclang-dev`, since `v4l2-sys-mit` runs bindgen. *That two columns of 12 fit the 800×600 minimum canvas* is now **440 px required against 458 available**, printed as `AOBS_WORDS` before the first paint and asserted by `ci/qemu-boot.sh` on every boot that draws.

**The paper can be checked, and the component that checks it is shared** ([#73](https://github.com/allisson/aobs/issues/73)): `aobs-core/src/entry.rs` is 02-core.md §4's six behaviours as one reducer over a fixed slot array — prefix matching with an exact match winning over a longer word, space commits, **no** auto-accept, an off-list keystroke that does not land, and the two correction keys — parameterised by wordlist and slot count so import and both halves of the encrypted backup drive the same code. The byte a keystroke puts in the buffer comes out of the **wordlist**, not out of the key, which is what makes a capital, a digit and a letter with a diacritic one refusal instead of three. What changes the failure path is whether an answer is known: with one, a wrong word is `Wrong(position)` — the slot stays empty, the buffer is dropped, the cursor stays where the repair is and every other slot is untouched, which is §4's *destroys nothing* as the shape of the state rather than as a promise. The checksum is deliberately **not** in the reducer (it covers the phrase as a whole and stays in `Mnemonic::from_indices`), and neither is `discard`, which the session model makes a restart rather than a state transition. `aobs/src/confirm.rs` is the retype: the mnemonic never reaches the shell, because what crosses is an `Entry` that already holds the answer and hands back only what the user typed; a rejection goes **back to the phrase** with that position marked and named, Escape returns there too, and there is no `restart` control anywhere on it. The screen is built from §3's own heights, so the 440-against-458 sum `AOBS_WORDS` already prints covers it — the live line sits inside the banner rather than below it for exactly that reason. A property test is the safety claim: **no sequence of keystrokes places a word we did not generate**, and it is what caught an eagerly-evaluated index in the first draft.

**A wallet can be loaded, and there is exactly one of it** ([#74](https://github.com/allisson/aobs/issues/74)): `aobs/src/load.rs` is 04-screens.md §5 — **one screen, always present, on every load path**, carrying the two parameters that enter at derivation rather than at generation. The network sits above the passphrase because the confirm control's label is a function of whether the field is empty, so the passphrase has to be the last thing touched; two rows with a disc of their own for *chosen* (which is not the same fact as *where the cursor is*), mainnet preselected, no forced pick. The field is **clear text, always, no toggle**, and rendering is the whole mitigation: the delimiters and the space mark are `«`, `»` and `·` — **outside printable ASCII by construction**, which is what makes the render unambiguous, and it is the retype caret's own argument made with code points instead of a 2 px rule, because a rule cannot follow a string that wraps and 128 characters at the floor wrap exactly once. Printable ASCII into a fixed 128-byte buffer, **128 accepted and 129 refused**, never trimmed, and a rejected keystroke named — unless it has no printable form, in which case it is dropped rather than announced, the same call `confirm.rs` makes. **Core needed nothing**: NFKD before PBKDF2 and the assertion that `"a"`, `" a"` and `"a "` derive three distinct seeds both arrived with [#70](https://github.com/allisson/aobs/issues/70). `aobs/src/session.rs` is ADR-0010 as the mechanism rather than the promise — a second `set` returns `Err` and hands the refused wallet back to be dropped — and it is deliberately **not a `static`**, because a `static` is never dropped and the wrapped master key would never be zeroized. `aobs/src/identity.rs` is §7's hub: the fingerprint is eight hex digits and is byte-identical on both networks, so the network line is the whole signal and states itself **in both directions, never as an absence**. Two things this build changed elsewhere: the router's Escape arm is now what [#69](https://github.com/allisson/aobs/issues/69) predicted it would have to be — once a wallet exists the start menu is not an answer, so Escape returns to the hub — and the frame's `move` grew a third link, because §7's *sign* and *verify* are **adjacent** camera rows and the old chain's stated bound was *no two adjacent*. **Walked on the built ISO**, on the `ramfb` fbdev tier at OVMF's default 800×600 GOP: create → 24 words → the full retype → the load screen with `«·hunt··2·»` and *9 of 128* → testnet picked → the hub with a real fingerprint, `1h` coin types and the two camera rows greyed. One `Down` on the hub hops both of them, §13's confirm returns to the hub byte-identically rather than to the start menu, and the appliance started **exactly once** across the whole walk. **Not a standing assertion, though:** that the two screens fit the floor is arithmetic plus that one reading (444 and 384 logical px against 458), not a printed line like `AOBS_WORDS` — 05-testing-and-release.md §6.2 names three console lines and a fourth is a ticket, not a decision to take here. And the first attempt at this walk booted a **stale staged binary**: `image/config/includes.chroot/usr/bin/aobs` is gitignored and `image/build.sh` only checks that it *exists*, so `ci/build-binary.sh` has to run before every `lb build` — §6's own finding, met in miniature.

**A hostile PSBT can be refused, and the refusal has to name itself** ([#79](https://github.com/allisson/aobs/issues/79)): `aobs-core/src/psbt.rs` is 02-core.md §7's structural half — `AOBS-R01`–`R05`, `R07` and `R15`, which is every refusal that needs no key material. `Rejection` is two arms because §7 is: bytes that never became a PSBT carry **no code** and return to scanning, and bytes that decoded and then failed carry a `Refusal`, which carries the code and one action. **Nothing here scans for duplicate keys** — the dependency rejects them in all three maps, so what this adds is the mapping and the alarm: `DuplicateKey` and `XPubKey("Repeated global xpub key")` both land on `R01`, and BIP-174's **invalid vector 5** is in the corpus so a future relaxation trips it. The `non_witness_utxo` rule is the stricter-than-Krux one and it is where the amount comes from: when both utxo fields are present the previous transaction **wins**, so an inflated `witness_utxo` buys nothing, and the test that proves it pays 200 000 out of a 100 000 input and is refused. Two sums in `u128`, because a wrapping add would turn *pays out more than it holds* into *pays out nothing*. `R15` is checked **first**, before anything walks: it is a property of the transaction, and a 2,000-output PSBT should be refused for what it is rather than for whichever output failed something else. **The corpus is `aobs-core/src/corpus_tests.rs`**, twenty-four named cases when it landed, at the crate root because the registry spans modules — and the bijection reads §6's tables out of `06-codes.md` with `include_str!`, so an invented code fails a test rather than shipping. Two readings it had to settle are now recorded in §7 itself: *in bijection* is between the two **sets of codes** (§5's own case list carries four cases on two codes, so one-for-one contradicts it), and the direction needing every code implemented is a `PENDING` list naming each owed code and its ticket, asserted to complete the registry exactly. §4's second fuzz target is here too — the PSBT parser on raw bytes, which retires the placeholder — with `-malloc_limit_mb` and `-max_len` at the transport bound, because *no unbounded allocation* is worth more as a limit libFuzzer enforces than as an assertion we write. **What #79 could not build:** the discard-only screen. There is no path a PSBT can arrive by until the camera lands ([#78](https://github.com/allisson/aobs/issues/78)), so the copy is a `reason()` on the typed variant, computed in core where standing rule 4 requires it, and the screen that states it is the scanning and review work's.

**The byte-compare that decides what *ours* means is in** ([#80](https://github.com/allisson/aobs/issues/80)): `aobs-core/src/derive.rs` is `Wallet::verify`, three verdicts over a claimed path and a `scriptPubKey`, and it is the function most of the product's security reduces to — a path is read for *where to look* and the bytes decide, so a path we would never scan derives nothing at all. `psbt.rs` is what each verdict means: `AOBS-R09` for the unscannable path, `AOBS-R08` for bytes that disagree, both refusing the **entire** transaction, and `AOBS-R06` when no input re-derives — four copy requirements on one code, two unconditional (the loaded network, account 0) and two selected by booleans (a passphrase in use, and *every* input declaring the other network's coin type, which is the symptomless case and which selects **copy only**). **There is now one entry point and it returns an `Accepted`:** `validate(wallet, bytes)`, the document paired with the model, because a caller who ran the structural half and forgot the second call would hold a transaction that looks reviewable and whose change was never re-derived — the attack itself, and pairing them is what keeps `Review` to exactly §9's list. The fingerprint is a hint on outputs and is not consulted for inputs at all, since for an input it would only gate a question the byte-compare answers outright. **One thing the spec did not answer and now does:** `Amount::MAX` is `u64::MAX` and two taproot inputs claiming it each pass every structural check, so **`AOBS-R16`** bounds the input sum by the money supply — checked before any key material, and it is what lets the model carry `bitcoin::Amount`s at all. The vsize the fee rate divides by sums weight units and charges the smaller signature element in every family, and it reproduces the published 1-in-2-out figures exactly: **141 vB P2WPKH, 225 P2PKH, 154 P2TR** — the 226 figure everyone quotes charges a 72-byte element, which we deliberately do not. §4's third fuzz target is here too, structure-aware over a *plan* rather than bytes, and it re-reads the accepted path with its own arithmetic rather than calling `verify` back — a target that asked the code under test whether it agreed with itself would assert nothing.

**The riskiest parser in the tree now has a wrapper in front of it** ([#77](https://github.com/allisson/aobs/issues/77)): `aobs-core/src/ur.rs` is 03-transport.md §2, §3 and §4 as one `Scanner` built for one `Class`, and the four bounds are checked in the order §3 states them — the symbol's length, the UR type, the class, `seqLen`, `messageLen` and the stream's identity, the parts budget, and only then the dependency. `AOBS-R10` names **both sides** and leaves the screen live; `AOBS-R11` is the 1,024-part budget, which bounds the *work* where `seqLen` only bounds the *claim*, and it is the only thing that stops a fountain animation feeding well-formed parts forever. Everything else that fails is a **discard with no code** — a bad scan says nothing and the user aims again (06-codes.md §4). Two classes never reach the fountain decoder at all, by construction: `Address` is plain text and `Backup` is single-part `ur:bytes`, so a multi-part stream at the restore prompt is refused rather than decoded. **Building it found what the spec could not have known:** `fountain::Part` is `pub(crate)` in every accessor that matters, so *before any part reaches `ur`* is unimplementable through the dependency's types and the clamp reads the part's CBOR header itself — safe only because both readers take the same bytes at the same offsets under the same width rules, which is what lets the bound on the *declared* `messageLen` stand for the *delivered* message. And **§4's *accepted* is load-bearing**: the first draft pinned the stream's identity before the decoder took the part, so one hostile frame with a plausible header could claim the stream and lock the honest animation out of the scan — a test now names that. §4's first fuzz target is here (`Vec<&str>` driving the wrapper, upstream ships none), and the same claim runs as a property test on every commit because the fuzz gate is a nightly job. The transport corpus is a **second table** in `corpus_tests.rs`, because §5's own transport list includes a bound that *accepts* and several that carry no code — a case states its outcome, and only the refusing ones enter the bijection.

**The camera answers, and the scanning screen is one screen** ([#78](https://github.com/allisson/aobs/issues/78)): `aobs/src/camera.rs` is 03-transport.md §5 — `VIDIOC_QUERYCAP` telling a USB UVC node from an IPU6 one, `GREY` before `YUYV` and never `MJPG`, and the largest size the device offers up to 1280×720. Three things the spec could not have known are now in §5a. **`v4l` does not name `V4L2_CAP_IO_MC` at all**, so the bit is written out here — but it does read `device_caps` rather than the driver-wide field, which is the one §7's distinction is actually about. **`FrameSizeEnum::to_discrete` is unusable**: for a stepwise or continuous device it materialises the whole cross product, which at step 1 over 1920×1080 is two million structs, so the resolution preference is arithmetic on the grid and only the discrete arm is enumerated. And **the drop policy is the buffer count** — with two mmap buffers exactly one frame is in flight while we decode, so the kernel does the dropping and *no queue* is structural rather than implemented; raising the count to smooth things out reintroduces the trap §5 names. `aobs/src/qr.rs` is `rqrr` at `default-features = false`, because its default feature is the `image` crate and the plane we already hold is what `image` would decode down to — §5's reason for rejecting `nokhwa`, applied to the crate §5 chose. `aobs/src/scan.rs` is 04-screens.md §11.1's one screen in three configurations, and **the configuration is two properties read off core's `Class`**: `wanted()` for the heading, which is the same phrase the wrong-class refusal names, and `multi_part()` for whether a fraction of parts exists to report at all. **The one branch on this screen asks rather than decides** — a wrong-class payload leaves the camera up and a spent budget ends it, and `Scanner::spent()` answers that instead of the shell telling two `Refusal` variants apart. Two capture threads can never hold the node at once — a thread holds a mutex for its whole run, because `leave` cannot join one blocked in `VIDIOC_DQBUF` and the `EBUSY` from a fast re-entry would have been reported as a camera that went away. The preview is published **before** the decode and has its own wake-up: capture and decode share one thread, which is what makes *no queue* true, and a 200 ms decode publishing second would hold the picture 200 ms behind the sensor — §5's own trap one level down. The decode path is a **recorded-frame corpus replayed from files**: eight raw V4L2 buffers in `aobs/frames/`, geometry in the table rather than in the file because a buffer is bytes and nothing else — `GREY`, `YUYV`, a padded stride, eleven degrees of rotation, a plain-text address, two symbols in one frame, and a frame with nothing in it; two of them replay as one animation through core's four bounds into the bytes the encoder started with. **They are synthesised, not photographed**, and that is named rather than glossed: they cover every way this crate can hand `rqrr` the wrong bytes and say nothing about the detector's tolerance, which is what 05-testing-and-release.md §6.3's real UVC camera is still for. **Walked on the built ISO**, on the fbdev tier at OVMF's 800×600 GOP, with a throwaway build that forced `camera-present` so the screen was reachable at all: it drew the heading, the camera-lost sentence with **no code** (06-codes.md §4 — nothing was refused), and the one row off it; pressing that row returned to the start menu with *scan an encrypted backup* now greyed, because taking the camera down re-probes. **What #78 could not build:** the screens a completed scan dismisses to. The review panel, the address verdict and the restore words are each a later ticket, so the payload is dropped and `Screen::Unbuilt` says so rather than swallowing the press.

**The screen the whole product reduces to is drawn, and the two numbers under it are measured** ([#81](https://github.com/allisson/aobs/issues/81)): `aobs/src/review.rs` is 04-screens.md §11.2 and §11.3 — one **non-scrolling** panel with the money facts beside the outputs above the design width and stacked above them below it, and **one full-width screen per payment address** on the way to §11.4's gate. Core needed nothing but a `pub use bitcoin`: the model, the byte-compare verdict and every formatter arrived with [#80](https://github.com/allisson/aobs/issues/80) and [#100](https://github.com/allisson/aobs/issues/100), so the whole of this ticket is turning a typed model into strings — the warning is one `match` over core's variant, and a second condition would be a compile error rather than a sentence someone forgot. **The two owed measurements are now printed lines**, `AOBS_REVIEW rows-required=447 rows-available=458 … address-required=699 address-available=752 address-one-line=yes` at the 800×600 floor, asserted by `ci/qemu-boot.sh` beside `AOBS_WORDS` — which retires the *waiting for the review panel* row in 05-testing-and-release.md §6.2 and fixes the six-output bound at six. **The address half is a font measurement, not our arithmetic**: `AddressBlock` holds a hidden `Text` carrying one 4-character group in the face and size it draws in, so the number is what the shipped ISO's DejaVu Sans Mono actually renders — §0's derived 698 was right to within a pixel — and a measurement that comes back zero prints `unknown`, which CI fails. 02-core.md §7's discard-only screen is here too, the one [#79](https://github.com/allisson/aobs/issues/79) deferred: the reason and the code both from core, one row, no *proceed anyway*. Its other half lands on the scanning screen instead — bytes that never became a PSBT carry no code, so the sentence goes up, the camera stays live and the decoder is replaced. **Walked on the built ISO** at the fbdev tier's 800×600: six rows non-scrolling under the stacked facts, two 62-character P2TR addresses each on **one line**, change labelled *re-derived from the seed at 84h/0h/0h/1/7 and matched byte for byte*, the warning inline on the fee row in crit red, then the walk — *Payment 1 of 5*, *2 of 5* — and Escape returning to a **byte-identical** panel. Building it found two defects a test could not have: a reflowing block built on a `Rectangle` reports no height and draws straight through what follows, and a fixed row height clips a wrapped address instead of growing. **Not walked:** the wide rail's *drawn* form, because QEMU's `screendump` on the DRM tier captures the console plane and not ours — the rail was walked in a throwaway forced-wide build at the floor instead, and its numbers stand on the console line.

**The product works: scan, review, hold to sign, and hand the signed PSBT back** ([#82](https://github.com/allisson/aobs/issues/82)). `aobs-core/src/sign.rs` is 02-core.md §8 — partial signatures added, **nothing removed and nothing finalized**, asserted field by field because the failure this exists for is a helpful `non_witness_utxo` strip that shrinks the document while every other field still checks out. `aobs-core/src/outbound.rs` is 03-transport.md §6, §8 and §9 as one type: ECC L, `Version::MIN`..v27 with `boostecl` pinned false, §9's 960-byte fragment length as a **parameter** so the property test can sweep it, and one branch — on a fragment count, never on bytes — for the single-part form that carries no `seq`. **Making `sign` unable to fail changed §7**: a taproot input must now declare its internal key (`AOBS-R05`, widened rather than given a code of its own, because BIP-371 makes that field the declaration that the spend *is* a key path), and the signing key source **ignores the fingerprint** the way §7's input rule already does — the dependency's own `GetKey` answers only for a matching fingerprint, so a transaction accepted under *"a coordinator that filled the fingerprint in wrongly should not make a wallet unsignable"* would have come back out with nothing in it. **The vectors are BIP-341's seven key-path cases, not BIP-340's rows**: only index 0 of BIP-340's CSV has all-zero auxiliary randomness, where all seven of BIP-341's do — which is exactly `sign_schnorr_no_aux_rand`, established against an independent BIP-340 implementation rather than read, and three of the seven carry a real merkle root so the **tweak** is asserted rather than assumed. **An owed measurement is discharged**: the predicted signed vsize the fee rate divides by, against transactions the suite signs and then finalizes by hand — 141/141 for P2WPKH, 154/154 for P2TR, and **225 predicted against 226 real** for P2PKH, which is the published 226 figure arriving from the other direction, since it charges the 72-byte DER element we deliberately do not. **Walked on the built ISO** at the fbdev tier's 800×600, and the walk found the defect a test could not have: the hold clock **counted ticks rather than time**, so 3.5 s of held key reached 97% of the bar on the software renderer — the clock is now `aobs/src/gate.rs`, an `Instant`, and the arithmetic is a function with tests. Re-walked: three 200 ms taps and a 2 000 ms hold leave the gate **byte-identical**, 4 500 ms signs, the single-part screen says **nothing at all** about parts while the four-part one states them once, two captures of a multi-part animation differ (fresh parts) and two of a single-part one do not, and *show the last signed transaction again* redraws a **byte-identical** screen — RFC6979 determinism visible on the panel. **One gap is named rather than closed:** a taproot input whose declared internal key is not the key its `scriptPubKey` is the tweak of passes every check and is then unsignable, and `06-codes.md` defines no code for it — so the document goes back out and the coordinator refuses it in seconds, which is a better trade than a crash and a 24-word retype. 02-core.md §8a records it and it is a ticket.

**That gap is closed, and reading the dependency is what decided how** ([#113](https://github.com/allisson/aobs/issues/113)). `bitcoin` 0.32 produces a taproot key-path signature **iff** `tap_key_origins` holds an entry keyed by exactly `tap_internal_key`, with empty leaf hashes, whose path our key source answers — the internal key's *value* is never compared against the key we derive, it is the map lookup and nothing more. That falsified the ticket's own recommendation: comparing the declared internal key against the untweaked key would have **refused transactions that sign**, because an internal key that is not the key the `scriptPubKey` is the tweak of but whose entry declares a byte-verifying path signs and finalizes correctly — so the new `AOBS-R17` it needed was not spent. What closed it instead is one rule in two halves, and **no new registry number**. Structurally, `AOBS-R05` widens again on #82's own BIP-371 argument: the declaration has two ends, the field *and* an origin entry keyed by it carrying no leaf hashes, and an input with only one has not declared the script type that row is about. On the derivation side, 02-core.md §7 gains rule 6 — **an input's claim is read out of the map its family is *signed* from**, `bip32_derivation` for BIP44/49/84 and the internal key's entry for BIP86 — so a claim anywhere else is not a claim about *this spend*, the input is simply not ours, and `AOBS-R06` is what fires. That closes the taproot case and an instance nothing had named: **a BIP44/49/84 input whose only byte-verifying claim sits in `tap_key_origins`**, which the old *walk both maps* rule called ours and the ECDSA signing path never touched. So `sign` now asserts what §8 always meant — **every input the validator found ours comes back signed** — with those indices travelling on a crate-private field of `Accepted`, which also makes *the only way to hold one is to have run every check* a property of the type rather than an argument about the call graph. **§4's third fuzz target gains a second invariant** — *every input it accepts as ours is one `sign` produces a signature for*, re-derived in the target with its own arithmetic and reached by a new `KeyPath` axis on the plan, which is why that target now signs. **The residual cost is named rather than glossed:** the hostile shape where our `scriptPubKey` is ours and the key-path claim is not lands on `AOBS-R06`, whose copy offers the passphrase, account 0 and the network — copy that misnames the cause for a shape no honest coordinator emits, which is the trade §7 already takes for R06's other variants. **One corner is left named rather than closed:** the assertion is about the document going out and not this call's delta, because `Psbt::sign` declines a taproot key path when `tap_key_sig` is *already* set — so a PSBT arriving with nonsense in that field satisfies it, and an added-a-signature assertion would be `AOBS-E04` on bytes an attacker chooses. That is [#115](https://github.com/allisson/aobs/issues/115) and a verification obligation, not a gap left silent. **Not walked on an ISO:** nothing on any screen changed, and the two crafted PSBTs are `docs/qa-checklist.md` rows.

**That corner is closed, and the number #113 saved is what closed it** ([#115](https://github.com/allisson/aobs/issues/115)). `sign` could promise the document going out carried a signature for every input the wallet owns and not that *this call put one there*, because `bitcoin` 0.32's key path declines an input whose `tap_key_sig` is already set — so a PSBT arriving with 64 bytes of nonsense in that field was accepted, drew an honest panel, took the three-second hold and went back out unchanged under *Signed*. Of the ticket's three shapes, **the refusal was chosen**: verifying the arriving signature puts signature verification into this crate on the signing path and still ends in `AOBS-E04`, and narrowing the screen's sentence hands the user a document the coordinator will refuse where a refusal costs them one scan. So `AOBS-R17` is spent, and **it is wider than the defect in two ways that are each a decision.** It covers **all five fields** — `partial_sigs`, `tap_key_sig`, `tap_script_sigs` *and* `final_script_sig`/`final_script_witness` — because BIP-174 has a Finalizer *remove* `partial_sigs` when it writes the final script, so the finalized pair is the same signature in the other encoding and refusing one while accepting the other draws the line where the attacker chooses; and it covers **inputs that are not ours**, because the check needs no key material and therefore runs before anything knows whose the input is, which is also the right answer on its own — single-sig means we are the only Signer there is. What that buys is one predicate becoming two: `sign` now asserts the **delta**, *arrived unsigned and comes back signed*, where *arrived unsigned* is R17's own five-field test shared with the check that refuses it and *comes back signed* is the narrow pair `Psbt::sign` writes — deliberately not the same predicate, so a `tap_script_sigs` entry cannot stand in for the missing key-path signature. **The dependency was read rather than assumed, and it decided the shape:** `bip32_sign_ecdsa` overwrites `partial_sigs` unconditionally and neither path consults `final_script_sig`/`final_script_witness`, so `tap_key_sig` is the *only* field that could ever have defeated a delta assertion — which is what makes the wider rule a consistency choice rather than a second fix. **§4's third fuzz target gains a third invariant** — *an input arriving with a signature already in it is never accepted* — on a new nested `Arriving` axis, nested for the same reason `KeyPath` is: a flat six-way enum would refuse five plans in six and starve the checks the target exists for. **Not walked on an ISO:** nothing on any screen changed except which refusal a crafted PSBT earns, and the four crafted cases are `docs/qa-checklist.md` rows.

**And *comes back signed* now names one field per family rather than either of two** ([#117](https://github.com/allisson/aobs/issues/117)). #115's assertion asked for a signature in `partial_sigs` **or** `tap_key_sig`, for every input regardless of family, where §8 means the field that input's family is *signed from* — `02-core.md` §7 rule 6 one layer down, and the same asymmetry `input_is_ours` already respects when it reads the *claim*. **It was not a live defect, and the reason is two coincidences rather than an argument:** `Psbt::sign` dispatches on `output_type(i)`, so a P2TR `scriptPubKey` reaches the Schnorr arm and `bip32_sign_ecdsa` is never called for a taproot input; and `AOBS-R17` is one ticket old and refuses an input arriving with `partial_sigs` set. Remove either and a taproot input of ours comes back with an ECDSA signature, no key-path signature, and a passing assertion — an assertion resting on the conjunction of a dependency's dispatch table and a refusal, stating neither. **What makes the rule sayable is that the family travels**: the structural walk had already classified every input, so `Accepted::ours` is now `Vec<OurInput>` — index and `InputScript` beside each other — rather than a bare `Vec<usize>` a second reader would have to re-classify from the `scriptPubKey`, which in a crate whose whole argument is that the check is the authority would be a second implementation of *which family is this*. **The test cannot pretend to reach the shape honestly, and says so:** those same two facts make it unreachable from outside the crate, so it builds the `Accepted` from inside the way `an_accepted_input_that_arrived_signed_is_a_crate_bug` does and plants the **family** rather than the signature — an honest BIP84 spend signs into `partial_sigs`, the family travelling beside it says taproot, and the per-family assertion is the one thing that notices. §4's third fuzz target's second invariant reads the same rule, restated from the `scriptPubKey` it already had to read: the one place where saying it twice is the point. **Not walked on an ISO:** nothing on any screen changed, and no crafted PSBT reaches this, which is the ticket's subject.

**And the thing both halves of the transport agreed on was wrong** ([#112](https://github.com/allisson/aobs/issues/112)). `03-transport.md` said *BC-UR / UR2, both directions* and never said what the UR **message** is, so the tree answered it by construction: `ur` 0.5.2 does no CBOR, `Scanner` handed a completed message straight to `psbt::validate`, `outbound` emitted the same thing because the two halves have to agree, and §9's arithmetic was written over it. **BCR-2020-006 defines the message as a CBOR byte string wrapping the PSBT, and both coordinators implement exactly that** — Sparrow's `CryptoPSBT.toCbor()` returns a `ByteString` and its `fromCbor` casts to one; Specter's bundled `ur-registry` wraps a `Buffer` and unwraps one. **Neither has a lenient path**: a PSBT's first byte `0x70` is a CBOR *text* string of 16, so Sparrow throws `ClassCastException` and Specter's `getData()` hands back something that is not the document. What we emitted was a signature nobody could broadcast, and what we accepted was three bytes long. `aobs_core::ur::wrap`/`unwrap` is now the pair, called from both halves in one commit, and it applies to **every UR the crate touches** — the wrapper is a property of the *type*, so `ur:bytes` cannot mean CBOR at the signing prompt and raw at the restore prompt, and §7's backup carries it too. **§9 did not move, and finding that out is the interesting part:** every figure in §9.2 and §9.3 was *already* computed over the wrapped message and reproduces exactly — 3 017 and 7 517 characters at the 4 096 row, 4 parts at v26 for the 3 744 B PSBT, 1 943/v26 at the single-part boundary and 1 017/v18 one byte over. Only which *payload* lands where moved: the boundary is a **957-byte PSBT**. **The instrument nothing in the tree could have been** is BCR-2020-006's own published vector — a 167-byte PSBT, its `58 A7` CBOR and its UR string, all three printed in the registry — now a checked-in fixture, and the one transport test we did not write both halves of; every other one asserts symmetry, which holds whichever convention we picked. **Building it found a second interoperability defect nobody had named:** §3's ordering requires we read `messageLen` before the dependency does, and our reader called `bytewords::decode` on the payload as scanned where `ur` lowercases first — so **every frame of an uppercase multi-part animation failed and was reported as a bad scan**. Specter emits exactly that (`qr-code.html`: `nextPart().toUpperCase()`), so the appliance could not read a Specter animation at all; single-part uppercase worked, which is why the one uppercase test in the tree passed. `ur.rs`'s own *two readers of one field is only safe if they cannot disagree* now covers case. **Not walked on an ISO** and not closed: the encoding question is settled on source, but *finalized, and broadcast* is `05-testing-and-release.md` §6.3's row and a verification obligation, with `docs/qa-checklist.md` carrying it in both directions.

## Settled — do not silently revisit

These came out of grilling and research. Reopening one is a deliberate act with a reason, not a drive-by.

- **Slint, not Tauri.** Tauri was the original premise and lost on measurement: 268 packages / 650 MiB against Slint's 22 / 21 MiB, and `getUserMedia` cannot work in a stock Tauri app on Linux. The UI is Slint on `backend-linuxkms-noseat` + `renderer-software`, with no X server, no compositor and no seat daemon. See `docs/research/05-tauri-viability.md`. (The *22 / 21 MiB* is now stale in our favour and owed as a measurement — `seatd` and `libseat1` left with ADR-0016.) The licence question this raised is settled: **the repo is GPL-3.0-only**, which is what Slint's GPL option requires and what removes an unresolvable ambiguity in its royalty-free licence. See `docs/adr/0001-gpl-3-0-for-the-slint-ui-toolkit.md`.
- **The display path is two tiers**, chosen at runtime by Slint's own `or_else`: a DRM dumb buffer where the machine has a DRM device, `/dev/fb0` via `efifb` where it does not. `simpledrm` — ADR-0009's mechanism — **does not exist on Debian**, which is what falsified it. `amdgpu`, `xe` and `radeon` are deleted from the image because firmware-less they take the framebuffer aperture and then fail. UEFI-only stands, but on build-and-test surface rather than on "no display path exists". See `docs/adr/0016-two-tier-display-path.md`; ADR-0009 is kept as a superseded record because *how* it was wrong is the standing rule's whole point.
- **The appliance answers its own power button, and the app dies before the machine does.** No D-Bus, so no `systemd-logind`: the power button is `KEY_POWER` on its own evdev node, read directly rather than through Slint's key path (Slint delivers it as a bare NUL, which any unnamed key also produces). *End the session* is the app exiting 42 — `SuccessAction=poweroff` takes the machine down **after** the process is dead and `init_on_free` has poisoned its pages, which is what makes the RAM wipe unconditional. Never replace this with `systemctl poweroff` or `reboot(2)`; both leave the seed in RAM while the machine goes down. *Restart* is `exit 0` and a fresh process, not a reboot. See `docs/adr/0017-the-appliance-answers-its-own-power-button.md`.
- **Air-gapped by construction.** The appliance has no network stack, no cloud, no sync, no broadcasting, no telemetry, no update check. Every feature is designed to work with the machine's networking physically absent.
- **QR is the only data channel**, both directions, using BC-UR / UR2 (`ur:crypto-psbt`). The physical keyboard handles seed import and passphrase entry. QR decoding happens in Rust (`v4l` → `rqrr`), never in a webview.
- **Single-sig only** across BIP44/49/84/86, mainnet plus testnet/signet.
- **Amnesic.** State lives in RAM for one session. There is no config file, no wallet database, no transaction history, no cache.
- **Backup crypto**: Argon2id m=64 MiB/t=3/p=4 → ChaCha20-Poly1305 over the BIP-39 entropy. The user cannot choose the password; it is 8 words drawn independently from the EFF long list, ASCII-space separated. It ships, narrowed: offered only after the mnemonic is recorded, and displayed only after the user types the 8 words back correctly. See `docs/adr/0007-encrypted-backup-ships-narrowed.md`.
- **One wallet per boot**, enforced by a `OnceLock` rather than by a test — no switch, no unload, no idle timeout, and restart is the sanctioned way to reach a different wallet. Signing is unlimited within a session, but only the most recently signed transaction is re-displayable. See `docs/adr/0010-one-wallet-per-boot.md`.
- **Six outputs, and a seventh is a refusal.** The review panel is non-scrolling, holds six rows in the 800×600 minimum canvas — **measured, 447 logical px against 458** ([#81](https://github.com/allisson/aobs/issues/81)), so the bound is fixed rather than provisional — and payment and change both count. Do not "fix" this by scrolling, clipping or summarising the remainder — Coldcard's `MAX_VISIBLE_OUTPUTS = 10` plus *"plus N smaller output(s), not shown here"* is the compromise our larger screen exists to avoid, and paging turns the limit into 200 pages nobody walks. Named cost: a batched payout above six outputs is split by the user. See `02-core.md` §7 and `04-screens.md` §11.2.
- **The network is a load parameter**, not a property of a seed: a two-state selector beside the passphrase, mainnet preselected, stated for a restore rather than asked. Testnet/signet sessions look identical to mainnet ones by design. See `docs/adr/0015-network-is-a-load-parameter.md`.

## Threat model

Defended: a compromised online host feeding malicious PSBTs, hostile bytes arriving over the QR channel, theft of the machine or boot media after shutdown.

Out of reach and openly so: malicious firmware, hardware implants, cold-boot and DMA attacks by a present adversary, cameras in the room.

The consequence that shapes the most code: **the transaction review screen is the mitigation.** If the user cannot verify what they are signing, no other property matters.

## Rules that bite while coding

The full list is `docs/specs/00-overview.md` under *Standing rules* — nine of them, and breaking one silently invalidates a chain of tickets. The ones that come up most:

- **Re-derive, never trust.** A PSBT's BIP32 derivation paths are an attacker-supplied assertion. Change outputs are re-derived from our own key material and byte-compared against the `scriptPubKey`. Every surveyed signer does this; so do we.
- **Everything crossing the QR boundary is hostile input.** `ur-rs` adopts an attacker-controlled `seqLen` and allocates on it, so limits are clamped at our call site. The PSBT parser and the UR decoder carry fuzz targets we write ourselves.
- **Secrets are wrapped in zeroizing types** and zeroized at session end. Secret material stays out of logs, error messages, and `Debug` output.
- **Coverage bar**: 95% production code, 98%+ on security-critical components, plus fuzzing, property-based tests, and the BIP test vectors. The spec names which components carry the 98% bar.
- **Verify the shipped artifact, not just the source.** Coldcard shipped a software PRNG for five years because a build-integration defect broke the linkage while the source stayed correct. Tests that only assert against the source tree would have passed.
