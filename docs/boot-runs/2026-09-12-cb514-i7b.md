## What it shows

**There was no aperture race.** The `sysfb` device is `vga-framebuffer.0`, which is the
`VIDEO_TYPE_VGAC` branch at `drivers/firmware/sysfb.c:159` — not `vesa-framebuffer` at `:157`.
`vesafb_probe` requires `VIDEO_TYPE_VLFB` (`vesafb.c:271`), so `vesafb` had nothing to bind even in
principle. `aperture` was in the grep and matched nothing across a ring buffer reaching back to
`0.006344`. `simplefb` registered unopposed.

**`vga=791` has never set a mode on this machine.** `0x317` is the hex of 791
(`arch/x86/boot/video.c:334`), routing to VBE `0x117` — 1024×768×**16bpp**. This framebuffer is
32bpp, and the mode list shows what SeaVGABIOS actually offers: `341`–`344`, i.e. VBE
`0x141`–`0x144`, an OEM range. Standard 1024×768×32 is `0x118` → `vga=792`, **also absent**. The
mode-set fails, the kernel prompts, and the 30 seconds elapse.

**The console was 1024×768 anyway, from coreboot.** `framebuffer-coreboot` registers a
`simple-framebuffer` from the coreboot table (`framebuffer-coreboot.c:64`). Coreboot's own mode is
1024×768 — which is also what `vga=791` asks for. **That coincidence is why a dead parameter
survived to M3 with three documents insisting it was load-bearing.**

## Findings

### `vga=791` is removed from the image, and the console guarantee moved into the appliance

There is no portable `vga=` value: `video-mode.c:88` matches a mode by `(mi->y << 8) + mi->x`, and
`video-vesa.c` fills those with pixels, so 1024×768 computes to `0x30400` and never fits the `u16`
it is compared against. `vga=836` (`0x344`) would work here and almost nowhere else. Recorded in
`docs/adr/0003-the-console-is-enforced-not-requested.md`; both `APPEND` lines in
`build/isolinux.cfg` now carry no `vga=`, matching `build/grub.cfg`.

### The startup floor was below the QR it exists to guarantee

Chasing what actually holds the console up found `aobs/ui/geometry.py` set `MIN_ROWS = 30` against
a QR display of 85 × 43. A 100 × 30 console passed the startup check and then clipped the emit
screen — the appliance's only path out. `tests/screentext.py:44` had recorded the clipping in a
comment and drove 128×48 to avoid picturing it. `MIN_ROWS` is now 43, and
`tests/test_emit_screen.py` asserts the floor against the rendered code rather than against the
number.

**This one is independent of the boot run and predates it.** It is recorded here because this run
is what caused anyone to look.

### `I-7`'s pass condition named the wrong floor

It required 43 rows and 85 columns — the QR's size, not the appliance's. The appliance refuses
below 100 × 43. Corrected in `docs/boot-checklist.md`.

## The confirming boot, after `vga=` was removed

Same machine, same day, on the rebuilt image — ISO
`682e52e00deac69172735143422e270c0d5b5888833d50f54a86bb892b1de78e`, 60.0 MiB, built 2026-09-12
09:46, with no `vga=` on either `APPEND` line and `MIN_ROWS = 43` in the shipped rootfs.

**The `Undefined video mode number: 317` line is gone, and so is the 30-second wait.** The boot goes
from `Probing EDD` straight into the kernel.

Inspection boot, verbatim:

```
# cat /proc/fb
0 simple
# cat /sys/class/graphics/fb0/name
simple
# stty size
48 128
# ls /sys/devices/platform/ | grep -i framebuffer
vga-framebuffer.0
```

**Byte-identical to the pre-change boot.** That is the point of the run: the console never came from
`vga=791`, so removing it cost nothing, and `48 128` is now an observation rather than an inference
from a parameter that was failing. `vga-framebuffer.0` is still present, which also settles a
smaller question — `sysfb` was registering the text-mode device all along, and `vga=791` had not
been suppressing it.

**One thing this run does not check, and no run on this machine can.** The refusal screen
`ConsoleTooSmallScreen` has never been drawn. This console is 128×48, comfortably above the 100×43
floor, so the path that makes the floor a guarantee is **unobserved** — the same shape as the UEFI
path, and it must not be written up as tested. What is tested is that the floor does not reject a
console that should pass.
