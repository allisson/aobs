### The BIOS console is `simple`, not `vesafb` — and the repository says it cannot be

`I-7` observed `fb0` named `simple`, at 1024×768 giving a 128×48 console. `simple` is the fb
identity `simplefb` reports; `vesafb` reports `VESA VGA`. The console size is exactly what the
repository predicts for `vga=791`, so the *mode* is right and no screen is affected — only the
driver that owns it.

This does not fit the mechanism the repository documents. In the pinned kernel's own config
(`boot/config-6.12.107+deb13-amd64`):

```
CONFIG_SYSFB=y
# CONFIG_SYSFB_SIMPLEFB is not set
CONFIG_FB_VESA=y
CONFIG_FB_SIMPLE=y
```

`docs/boot-pipeline.md:466` cites that unset symbol as the reason the BIOS path lands on `vesafb`.
With it unset, `sysfb` should register a `vesa-framebuffer` device and `simplefb` should never bind.
It bound anyway.

**Not diagnosed in this run**, and deliberately not guessed at. **Diagnosed on 2026-09-12 by the
`I-7b` run — `docs/boot-runs/2026-09-12-cb514-i7b.md` — and the answer is not the one this section
expected.** `simplefb` did not beat `vesafb`: `vesafb` was never offered a device, because
`vga=791` never set a video mode on this machine at all. Every statement listed below is corrected
in that run's PR, along with `build/isolinux.cfg`, which no longer carries `vga=`.

Until that run, these statements were unsupported rather than wrong, and none of them had been
edited:

- `docs/console-appearance.md:29` — the chain `vga=791` → `vesafb` → `fbcon`, marked **observed** on
  the target machine in M3. This run is that observation, and it does not show `vesafb`.
- `docs/boot-pipeline.md:457`, `:466`–`:467`, `:480`
- `build/modules.allow:25`–`26`
- `docs/roadmap.md:353`, `:529`, `:531`
- `docs/overview.md:153`, `README.md:493`

Neither `build/verify.py`'s `FB_VESA` assertion nor any checklist row is invalidated: `FB_VESA=y` is
still true of the image, and `I-7` passes on the conditions it actually states — a framebuffer
exists and the console clears 43×85.

### `I-9`'s octal fallback is itself the trap it warns about

`docs/boot-checklist.md:~205` offers this as the shell alternative to the `python3` form:

```
printf 'U+2588 [\0342\0226\0210]  U+2591 [\0342\0226\0221]  U+0021 [!]  U+002D [-]\n'
```

It printed:

```
U+2588 [260]  U+2591 [261]  U+0021 [!]  U+002D [-]
```

No glyph was tested. dash's `printf` consumed `\0` plus **two** further octal digits, not three, and
printed the leftover digit literally: `\0342` → `\034` (0x1C, an invisible control) + `2`; `\0226` →
`\022` + `6`; `\0210` → `\021` + `0`, giving `260`. `\0342\0226\0221` gives `261` by the same
arithmetic. Both match the screen exactly.

`\0ddd` with three digits is the form for a **`%b` argument**, not for the format string. In the
format string it is `\ddd`. Two corrected forms, **neither observed on the machine** — this run
answered the row with the `python3` form instead:

```
printf 'U+2588 [\342\226\210]  U+2591 [\342\226\221]\n'
printf '%b\n' 'U+2588 [\0342\0226\0210]  U+2591 [\0342\0226\0221]'
```

The row already carries a "do not fix this back" note, written after `\xHH` failed the same way.
That note is right about `\xHH` and wrong about what replaces it, so a correction has to keep the
warning and change the form — reverting to `\xHH` would be the third wrong answer.

**Also unusable as written**: the `python3` form prints the literal characters `█` and `░`, which
cannot be typed on the console under test. A Python `█` / `░` escape is what was actually
run, and it is the form the row should offer:

```
python3 -c 'print("U+2588 [█]  U+2591 [░]")'
```

### The booted image's digest was recovered, not captured

The record has to say which image was booted, and for a while it could not. `m3-handoff.md` records
the ISO built from `460b475` as `51c7d664…04aab`; `out/bitcoin-signer-amd64.iso` hashes to
`3aa115ad…0a2c1` with an mtime of 2026-09-11 19:24, after the handoff was written. Both are builds
of the same commit. The operator resolved it from memory — the stick was rebuilt and rewritten from
the 19:24 build — and that attestation is why the Image block above names a digest. **It is
testimony, not a measurement taken at the time.**

This is **not** evidence of tampering or of a content difference. The reproducibility contract is
due in M4 — `docs/reproducible-build.md` does not exist yet and `docs/threat-model.md:166` claim
(ix) says so — so two builds of one commit are expected to differ byte for byte at this stage. What

The gap is procedural and it belongs in `docs/boot-checklist.md`: the checklist asks the record for
a digest but never tells the operator to take it at the moment the stick is written, which is the
only moment it can be taken from the thing that actually boots. A digest recovered afterwards from
a build directory is a guess about history.

### The descriptor screen labels a testnet4 wallet `bc1q`

`S-4`'s export screen rendered with the footer `BIP84 · bc1q`, on a wallet whose own loaded screen
had just said `network testnet4`. Every address this wallet produces begins `tb1q`.

### The camera was not found on this machine, and it worked here before

The first session boot reached the home screen with `No camera was found, so the paths that scan a QR
code are unavailable this session.` and `Restore from an encrypted wallet QR` annotated `needs a
camera`. The operator reports the camera worked on this machine on an earlier image.

This blocks the gate rather than one row: the PSBT's only way in is the camera, so `S-6`, `S-7`,
`S-8` and `S-9` cannot be answered while it holds.

What is already ruled out, from the tree rather than from the machine:

- `uvcvideo` is in `build/modules.allow` and `I-6` observed `drivers/media` carrying `usb`,
  `v4l2-core`, `common` and `mc` in the built image.
- `build/init` and `build/prune_modules.py` are **unchanged** since `7bb2feb` (#10).
  `build/modules.allow` changed in `460b475` in comments only — no line added or removed from the
  seven module names.

So the regression is not in the module allowlist or in PID 1, and the cause is undiagnosed. The
detection itself is `aobs/ui/app.py:203` `_camera_present()`, which pulls **one frame** through the
whole `v4l2` path — so "no camera" here means no frame, which a missing node, a failed open, a
format negotiation that found nothing usable and a streaming timeout all produce identically.

Leading hypothesis: `build/init` step 4 closes the bus with `authorized_default=0` after a fixed
`sleep 2`, and an internal camera that enumerates after that line is deauthorised and never binds.

**The fault is intermittent, and that is observed, not argued.** A power-cycle and a second session
boot off the same medium found the camera normally. Same image, same PID 1, same machine, opposite
outcome — which rules out anything static in the image and leaves timing. It does not by itself
prove the `sleep 2` is the timer that lost: it makes it the only candidate anybody has, and an
intermittent fault that nobody has caught in the act is not a diagnosed one.

**A one-in-two camera is a defect in its own right**, separate from whether it blocks a given run.
The user-visible failure is silent and plausible — the appliance says a camera was not found, which
is exactly what it would say on a machine that has none — so an operator with no reason to doubt it
loses the scan paths for a session and never learns the camera was there. Writing that up, and
deciding whether step 4 should wait for the devices it expects rather than sleep a constant, is
post-gate work in `docs/roadmap.md`, not a change to make mid-run.
