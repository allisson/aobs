# Does `bitcoin` 0.32.x reject duplicate PSBT keys?

Research findings for [aobs#32](https://github.com/allisson/aobs/issues/32). Map: [aobs#1](https://github.com/allisson/aobs/issues/1).

Pinned at tag **`bitcoin-0.32.11`**, the highest conventional 0.32.x patch release. Every claim below is
read from that tag's source, not from docs.rs prose. (Tags `bitcoin-0.32.100`, `.101` and `.102` also
exist in the repository and were not examined.)

---

## Answer

**It rejects. Every duplicate key is an error on the deserialization path, in every map, with no
silent collapse into a `BTreeMap` and no last-write-wins.**

So [#13](https://github.com/allisson/aobs/issues/13)'s duplicate-key refusal is satisfied by the
dependency, and **the pre-parse scan [#10](https://github.com/allisson/aobs/issues/10) provisionally
required does not need to be built.** What aobs owes instead is a *test* asserting the property, not
an implementation of it — see [§5](#5-what-this-means-for-the-spec).

---

## 1. The call chain, traced end to end

`Psbt::deserialize` is a thin wrapper; the work happens in `deserialize_from_reader`
([`psbt/serialize.rs:79`](https://github.com/rust-bitcoin/rust-bitcoin/blob/bitcoin-0.32.11/bitcoin/src/psbt/serialize.rs#L79)):

```rust
pub fn deserialize(mut bytes: &[u8]) -> Result<Self, Error> {
    Self::deserialize_from_reader(&mut bytes)
}
```

which checks the magic and separator, then dispatches to exactly three decoders
([`psbt/serialize.rs:84`](https://github.com/rust-bitcoin/rust-bitcoin/blob/bitcoin-0.32.11/bitcoin/src/psbt/serialize.rs#L84)):

```rust
let mut global = Psbt::decode_global(r)?;
global.unsigned_tx_checks()?;
...
for _ in 0..inputs_len  { inputs.push(Input::decode(r)?); }
for _ in 0..outputs_len { outputs.push(Output::decode(r)?); }
```

All three reject duplicates, by three different mechanisms that happen to agree.

## 2. The global map: an explicit branch per key type

`decode_global` loops over `raw::Pair::decode` and matches on the key type
([`psbt/map/global.rs`](https://github.com/rust-bitcoin/rust-bitcoin/blob/bitcoin-0.32.11/bitcoin/src/psbt/map/global.rs)).
Every branch guards its own slot:

| Key | Line | On a second occurrence |
| --- | --- | --- |
| `PSBT_GLOBAL_UNSIGNED_TX` | `global.rs:107` | `Err(Error::DuplicateKey(pair.key))` |
| `PSBT_GLOBAL_VERSION` | `global.rs:171` | `Err(Error::DuplicateKey(pair.key))` |
| `PSBT_GLOBAL_PROPRIETARY` | `global.rs:184` | `Err(Error::DuplicateKey(pair.key))` — `btree_map::Entry::Occupied` |
| *(anything else)* → `unknowns` | `global.rs:191` | `Err(Error::DuplicateKey(k.key().clone()))` — `Entry::Occupied` |
| `PSBT_GLOBAL_XPUB` | `global.rs:137-142` | **`Err(Error::XPubKey("Repeated global xpub key"))`** |

The xpub row is the one inconsistency and it matters for our error mapping, not for our security: it
is still a hard error, but it arrives as a **different variant**, guarded by
`.insert(...).is_some()` rather than by a vacant-entry match. Source comment: *"Keys, according to
BIP-174, must be unique"*.

Note the `_ =>` arm: **unknown key types are duplicate-checked too**, so an attacker cannot smuggle
repeats past the match by inventing a key type.

## 3. Input and output maps: the macro is where the guarantee lives

`Input::decode` and `Output::decode` are generated by `impl_psbtmap_decoding!`
([`psbt/macros.rs:56`](https://github.com/rust-bitcoin/rust-bitcoin/blob/bitcoin-0.32.11/bitcoin/src/psbt/macros.rs#L56)),
which loops `rv.insert_pair(pair)?` until `NoMorePairs`. Each `insert_pair` dispatches to
`impl_psbt_insert_pair!`, which has exactly two arms and **both error**
([`psbt/macros.rs:83-111`](https://github.com/rust-bitcoin/rust-bitcoin/blob/bitcoin-0.32.11/bitcoin/src/psbt/macros.rs#L83)):

```rust
// singular field (witness_utxo, sighash_type, tap_internal_key, ...)
if $slf.$unkeyed_name.is_none() { ...set it... }
else { return Err(Error::DuplicateKey($raw_key).into()); }

// keyed map (partial_sigs, bip32_derivation, tap_script_sigs, ...)
match $slf.$keyed_name.entry(key_val) {
    Entry::Vacant(empty_key) => { ...insert... }
    Entry::Occupied(_) => return Err(Error::DuplicateKey($raw_key).into()),
}
```

The singular arm is the one the ticket worried about, and it is an `is_none()` guard — **not** an
assignment that would overwrite. The keyed arm never calls `insert` on an occupied entry, so nothing
is replaced and nothing is merged. Proprietary and unknown keys are handled by hand at
`map/input.rs:356-370` and `map/output.rs:76-105`, both `Entry::Occupied → DuplicateKey`.

### The typed-key subtlety, and why it is harmless

The keyed arm deserializes the raw key bytes into a **typed** key (`PublicKey`, `XOnlyPublicKey`,
`ControlBlock`, …) before the `BTreeMap` lookup, so the uniqueness check is over typed keys rather
than raw bytes. This cannot weaken the guarantee we need: BIP-174 defines a duplicate at the byte
level, and byte-identical keys necessarily deserialize to identical typed keys, so they always land
on `Entry::Occupied`. The only direction the mapping could distort is *stricter* — two distinct byte
encodings collapsing to one typed key would reject a technically-non-duplicate PSBT.

## 4. Upstream proves it with BIP-174's own invalid vector

Not an inference from source shape — the behaviour is pinned by tests
([`psbt/mod.rs:1710` and `:1717`](https://github.com/rust-bitcoin/rust-bitcoin/blob/bitcoin-0.32.11/bitcoin/src/psbt/mod.rs#L1710)):

```rust
#[should_panic(expected = "DuplicateKey(Key { type_value: 0, key: [] })")]
fn invalid_vector_5() { hex_psbt("70736274ff0100750200000001...").unwrap(); }
```

That is **BIP-174 invalid vector 5**, the specification's own duplicate-key case, in both hex and
base64 form. It is already on the list of BIP vectors the map requires us to carry, so asserting it
costs nothing new.

## 5. What this means for the spec

1. **Do not build the pre-parse scan.** #10 promoted it conditionally; the condition is false.
2. **Assert it anyway, as a dependency-behaviour test.** The refusal in #13 now rests on a third
   party's invariant, so the suite must contain BIP-174 invalid vector 5 asserting that
   `Psbt::deserialize` errors. If a future `bitcoin` release relaxes this, that test is the alarm —
   which is the same reasoning #23 applied to build integrity: verify the property, not the intention.
3. **Map `Error::XPubKey("Repeated global xpub key")` onto the duplicate-key refusal**, alongside
   `Error::DuplicateKey`. #13 requires a refusal to name its reason; a duplicate global xpub that
   surfaced as a generic xpub-parse failure would name the wrong one.
4. **Two refusals arrive free and should be recorded rather than re-implemented**:
   `unsigned_tx_checks()` enforces BIP-174's empty-scriptSig/empty-witness rule on the unsigned
   transaction, and `PartialDataConsumption` rejects a global unsigned-tx value with trailing bytes.

### Allocation, checked while we were here

`deserialize_from_reader` does `Vec::with_capacity(global.unsigned_tx.input.len())`, which is an
attacker-influenced count — the shape that made `ur-rs` dangerous in
[#2](https://github.com/allisson/aobs/issues/2). It is **not** the same hazard class: that length
comes from a transaction that has already been fully decoded from bytes actually present, so it is
bounded by the payload size (each `TxIn` costs ≥ 41 bytes on the wire), and #13 already caps the
payload at 64 KiB. `ur-rs`'s `seqLen` is a *claim* that costs 4 bytes to make; this is a count that
costs 41 bytes each to make.
